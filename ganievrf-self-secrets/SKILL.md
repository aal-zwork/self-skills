# ganievrf-self-secrets

## Модель

- **Password-store** — git-репозиторий зашифрованных GPG-блобов,
  синхронизируется с S3 как remote. Безопасно хранить постоянно (зашифровано).
- **Мастер GPG-ключ** — живёт только на локальной машине пользователя,
  никогда не копируется на VM.
- **VM-ключ** — мастер-ключ выпускает отдельный ключ под конкретную VM;
  доставка — ручной защищённый канал (курица/яйцо: до доставки VM не может
  расшифровать pass-store из S3).
- **Сессия** — расшифровка только в `gpg-agent`/`ssh-agent` (память) и на
  tmpfs; ничего не остаётся на диске после закрытия сессии.

## Пути в pass-store

- Облачные секреты: `providers/<provider>/<kind>/<name>`
  (сейчас — `providers/yandex_cloud/...`).
- Внешние секреты: `external/<system>/<name>`
  (например `external/github/deploy-key`).

Каждый источник секретов обязан иметь **и создание, и обновление/ротацию**
через один интерфейс (`create-secrets.sh` + `update-secrets.sh`) — не
только разовое создание.

## Команды (репозиторий `secrets`)

- `make secrets` — создаёт/ротирует облачные и внешние секреты на машине,
  где вызван (без ssh-проброса).
- `make gpg-issue-vm-key VM=<id>` — **строго локально**, никогда на VM.
  Выпускает GPG-ключ под конкретную VM, печатает путь к временному файлу
  для ручной доставки.

Обе цели спрашивают подтверждение, если не задана
`GANIEVRF_MAKE_ASK_SKIP=yes`.

## Что никогда не покидает локальную машину

Мастер GPG-ключ. Ни в каком виде — ни целиком, ни зашифрованным "для VM" —
он не появляется в S3, GitHub или на какой-либо VM.

## Замена провайдера

Секреты именуются с префиксом провайдера именно для того, чтобы можно было
держать секреты двух провайдеров одновременно на миграции и постепенно
переключать `cloud_provider` (см. `ganievrf-self-ansible`), не теряя
историю старого провайдера.
